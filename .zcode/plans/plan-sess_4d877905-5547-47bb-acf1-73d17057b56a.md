# architecture-history 数据治理实施计划

## 目标与已确认决策

把 architecture-history 从"全量数据堆在 git"重构为"**本地 SQLite 权威库 + 线上精简 JSON 投影**"两层架构,并在此基础上推进关系图谱的可信化(核心目标:梳理建筑师之间的师生/同僚/雇佣关系)。

已确认的 4 个架构决策(用户拍板):
1. 本地库用 **SQLite**(方案 2,可查询),不是纯 JSON+gitignore
2. claims.json **全量留线上**(16MB,方案 A)
3. source-snapshots 下沉后 manifest **保留 sha256 审计**
4. 关系审核**先扩 verified 基数再审关系**(推荐路径)

执行顺序:① 下沉瘦身 → ② 建 SQLite → ③ 扩 verified → ④ 关系审核。

## 阶段 1:仓库瘦身(下沉 source-snapshots + catalog shard 出 git)

### 现状证据
- git 跟踪的 architecture-history 数据:catalog shard 20MB + claims 16MB + 3 个 source-snapshot 共 6.7MB + LFS pointer(hydration 71MB 实体在 LFS)
- validate.py L294/L309/L2420:对 catalog/snapshots 都是 `if exists()` 守卫,**不强制存在**
- test_page_contract.py L183-184:**显式断言 loader 不引用** source-snapshots/ 和 catalog/
- data-loader.js L87:前端只校验它 fetch 的 8 个文件,**不校验** source-snapshots/catalog
- build.py L248 `input_paths()` 用 `DATA.rglob("*.json")`:本地存在就进 data_version 哈希

### 要做的事
1. **引入 `ARCH_HISTORY_LOCAL_DATA` 环境变量**(或复用 build.py 已有的 `ARCH_HISTORY_ROOT`):
   - build.py / validate.py / import_wikidata_pilot.py / fetch_wikidata_pilot.py 的 `SNAPSHOT_DIR` / `CATALOG_DIR` 改为从本地数据根解析
   - 默认回退到 `assets/data/`(保持向后兼容,本机现有文件不挪动也能跑)
2. **.gitignore 新增**(architecture-history 级):
   - `assets/data/source-snapshots/`(整个目录)
   - `assets/data/catalog/`(整个目录)
3. **manifest 的 files 段保留这些路径的 sha256**:`derive_manifest` 改为"如果本地存在就算 hash 登记审计,不存在就跳过",但**已登记的 hash 不因文件下沉而从 manifest 删除**——这样审计链接不断。
4. **`git rm --cached`** 把 catalog shard + 3 个 snapshot 从 git 索引移除(本地文件保留)。LFS 的 hydration pointer 也一并 untrack。
5. **更新 AGENTS.md §architecture-history**:记录"source-snapshots + catalog 是本地数据,首次 clone 需跑 fetch+import 重建或从本地备份恢复"。

### 验证(done criteria)

- `python3 tools/build.py` 在本地文件仍在时**成功**(产出不变的 6 张表,因为 catalog shard 还在本地)

- `git status` 显示这些文件为 deleted(从 git 角度),`du -sh .git` 显著缩小

### 风险与回退
- 风险:data_version 哈希变化导致 data-loader.js 的 DATA_VERSION 更新——这是预期的(数据集边界变了),前端会正常重新加载
- 回退:`git revert` + 删 .gitignore 条目

## 阶段 2:SQLite 权威库

### 现状证据
- china-housing 的 housing.db(4.5MB)是 source of truth 的成熟范例,但它是**进 git** 的(因为小);architecture-history 的本地库(含 71MB hydration)**不进 git**
- 当前数据流:fetch_wikidata_pilot → source-snapshots(71MB) → import_wikidata_pilot → catalog shard(20MB) → build.py → 6 张表(线上)
- 关系分析需求(P0):需要跨表查询"两端点都 verified 的关系""空 credits 作品的 attribution 分析"——JSON 不适合,SQLite 适合

### 要做的事
1. **新建 `tools/db.py`**:SQLite schema + 导入/导出工具
   - 路径:`<repo>/demos/architecture-history/data/architecture-history.db`(**.gitignore**,类似 china-housing 但不进 git)
   - 7 张主表(对应 schema.json 的 entity 定义):`people` / `practices` / `places` / `works` / `relations` / `claims` / `sources`
   - 关联表:`claim_evidence`(claim 的 evidence 数组展开)、`work_credits`(work.credits 展开)、`source_snapshots`(登记本地快照的 id/path/sha256)
   - 字段:实体表用 JSON 列存全字段 + 提取关键索列(id/verification_status/confidence/entity_type/region/period)做 WHERE/JOIN
2. **`db.py import`**:从 catalog shard + 线上 JSON 灌入 SQLite
3. **`db.py export`**:从 SQLite 导出 6 张表 JSON(可选,作为 build.py 的替代数据源——本期不强制切,先让 SQLite 作为查询/审计副库存在)
4. **关系分析查询**(支撑阶段 3/4):
   - `SELECT * FROM relations WHERE from_id IN (SELECT id FROM people WHERE verification_status='verified') AND to_id IN (...)` —— 找可升级的关系
   - `SELECT w.id, w.name_en FROM works w WHERE NOT EXISTS(SELECT 1 FROM work_credits c WHERE c.work_id=w.id)` —— 空 credits 作品
5. **AGENTS.md 记录**:architecture-history 的本地库约定(路径、重建命令、不进 git)

### 验证
- `python3 tools/db.py import` 成功,行数 = 线上 JSON 实体数
- `python3 tools/db.py verify`:对每张表做 count + 抽样字段比对,与 JSON 一致
- 关系分析查询能出数
- `architecture-history.db` 不在 `git ls-files` 里

### 本期边界
SQLite 本期作为**研究/审计工作台**存在,不替代 build.py 的数据源。未来可以让 build.py 从 SQLite 导出(阶段 2.5,本期不做)。这样阶段 2 是纯新增、零回归风险。
